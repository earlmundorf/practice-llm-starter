#### Phase 0-prep — Pre-migration safety net (mandatory, both strategies)

Run BEFORE either strategy's Step 0.1. Code is git-rollback-able; databases, search indexes, and external contracts are not. These steps are mandatory for any migration touching production data; they are strongly recommended even on dev environments because the cost is small and they enable diff-based verification later.

- [ ] **Step 0.0a — Database backup (conditional on intake 4.1).** Behavior depends on the persistence scenario captured in `migration-docs/intake.md`:
  - **Scenario A (HSQLDB / in-memory):** SKIP. Document in `migration-log.md`: "no DB backup — HSQLDB in-memory; restart wipes anyway."
  - **Scenario B (ImpEx-seeded dev):** SKIP DB backup but git-tag the ImpEx source (`coredata` + `sampledata` extensions) so re-init is reproducible. Document in `migration-log.md`: "no DB backup — re-init from ImpEx; source tagged at commit X."
  - **Scenario C (prod with backup capability):** EXECUTE per intake 4.2's mechanism. Example: `mysqldump --single-transaction --routines --triggers <db> > migration-docs/baseline-db-{{DATE}}.sql.gz` (or RDS snapshot). **Verify restorable**: load the dump on a scratch instance before proceeding. A backup not proven restorable is not a backup.
  - **Scenario D (prod without backup):** ⛔ **HALT — plan blocked.** Do not proceed with the migration until backup capability exists. The skill's intake step (SKILL.md Phase 1 Step 3) should have caught this; if you're here, return to intake. See `references/known-incidents.md` incident 7.
  - **Scenario E (session-only):** SKIP. Document in `migration-log.md`: "no DB backup — session-only persistence; loss expected per intake 5.2."
- [ ] **Step 0.0b — Solr core export (conditional on intake 4.3).**
  - **If intake 4.3 = "rebuild from DB"**: SKIP backup. Document in `migration-log.md`: "no Solr backup — `solr_FullProductIndex` cronjob will rebuild; expected re-index time per intake 4.3 = N hours." Confirm the indexer cronjob is functional on the legacy stack before relying on it.

Major-version Solr bumps invalidate the index format; restoring is the only fast path back. Re-indexing 5M+ docs in production is hours, not minutes — see Gate 6 estimate.

### Phase E — Tests  (runs alongside D)

Authoritative ref: `references/sap-docs/07-testing.md`. Canonical execution path: **direct ant**, not Gradle (see Step E.0).

#### E.0 — Use direct ant, not `./gradlew yunittests`

The `sap.commerce.build` Gradle plugin (5.0.2 confirmed) **silently ignores** the `-Dtestclasses.extensions=...` filter — `./gradlew yunittests -Dtestclasses.extensions=<ext>` runs the full ~11000-test platform suite regardless. Wastes 10+ minutes and dilutes signal. Phase E uses platform-bundled ant directly. See `findings/2026-04-30-yunittests-ignores-extension-filter.md`.

```bash
cd core-customize/hybris/bin/platform
source ./setantenv.sh   # required — sets ANT_OPTS with JDK 21 module exports
```

After the source, every `ant <target>` invocation in this phase has the right environment.

#### E.1 — JUnit tenant initialization (one-time)

SAP Commerce integration tests (anything `extends ServicelayerTransactionalTest` / `ServicelayerTest` and annotated `@IntegrationTest`) run against the **junit tenant**, which has its own DB schema (`junit_*` table prefix, separate from `master`'s `*`). This schema is **NOT** created by `yinitialize` — that initializes only the master tenant. Without a junit-tenant init, every integration test fails with:

```
Caused by: java.sql.SQLSyntaxErrorException: Table '<db>.junit_metainformations' doesn't exist
```

- [ ] Confirm `installed.tenants=junit` is set in `dev-config/local.properties` (declares the tenant exists; required before init).

#### E.3 — Integration tests, scoped to all custom extensions

```bash
ant integrationtests -Dtestclasses.extensions=<comma-list> -Dtestclasses.annotations=integrationtests
```

Integration tests use the junit tenant initialized in E.1. They run inside transactions that roll back per test, so they don't pollute master-tenant data — but they DO need their own test ImpEx fixtures (typically loaded via `importCsv(...)` in a `@Before` method).

**Common gotcha:** if your test ImpEx fixture sets up a `BaseStore` for warehousing/stock-related tests, it must include `defaultAtpFormula(code)` and an accompanying `AtpFormula` row. Without it, `commerceStockService.getStockLevelForProductAndBaseStore(product, store)` returns 0 even when `StockLevel` records exist. Easy to miss because the master-tenant essentialdata typically has it, but a hand-derived test fixture often doesn't.

#### E.4 — Migration-specific verification points

These are the migration-tax items to confirm during the runs above (don't need separate test invocations — they manifest as failures in E.2/E.3 if not addressed):

- [ ] **JUnit 4 → 5 migration.** SAP Commerce 2211-jdk21.x bundles JUnit Platform 1.10.2. Custom tests that still use `@org.junit.Test` (JUnit 4) work via the vintage engine; new tests should use `org.junit.jupiter.api.*`. Don't migrate existing JUnit 4 tests purely for the sake of it — they pass under the vintage engine and the migration is independent of the platform bump.
- [ ] **Mockito 3 → 5.** Phase B.4 already renamed `org.mockito.Matchers` → `org.mockito.ArgumentMatchers`; verify zero references remain in the test sources.
- [ ] **`@TestExecutionListener` registration.** Spring 6.0 changed how test listeners register in some base classes; if any custom `TestExecutionListener` extends an SAP base class, confirm context init still succeeds.
- [ ] **`ycommercewebservicestest` test extensions.** If the project derives from this template, review HttpComponents 4 → 5 request-building code in test sources (separate from the production code path covered in Phase B.12).

#### E.5 — Why not Gradle

Recap for future readers: `./gradlew yunittests -Dtestclasses.extensions=<ext>` does NOT narrow the run on the `sap.commerce.build` plugin (5.0.2 verified; possibly fixed in a later plugin version, re-test if your project uses 5.1+). The full platform suite runs (~11000 tests, 5–15 min depending on hardware) and any per-extension filter is silent no-op. For migration validation, what matters is:
1. Custom extensions compile cleanly under JDK 21 + Spring 6 (verified by `./gradlew yall` in earlier phases).
2. Zero failures in `com.<your-package>.*` test classes.
3. The full platform suite's pre-existing failures (if any) are unchanged from baseline — they are NOT migration regressions.

If you DO want a full-suite Gradle run for completeness, run it AFTER the direct-ant runs in E.2/E.3 are green. The Gradle run takes ~10 minutes and should report 0 failures in your custom packages.
